# 평가 세트 작성 규칙

평가 세트는 **가상 포트폴리오 12개 × 공고 2개 = 24 케이스**입니다. 모두 직접 만든
가상 데이터입니다. 실존 인물·회사의 포트폴리오나 공고를 쓰지 않습니다(실제 데이터는
`eval/private/`, 커밋 금지).

## 파일과 이름

| 종류 | 위치 | 이름 |
|---|---|---|
| 포트폴리오 | `eval/cases/portfolios/` | `pf-{직무군}-{01~03}.json` |
| 공고 | `eval/cases/jobs/` | `jd-{케이스}.md` (예: `jd-dev-01a.md`) |
| 정답 라벨 | `eval/labels/` | `{직무군}-{01~03}{a,b}.yaml` (예: `dev-01a.yaml`) |

직무군: `dev`(개발) · `design`(디자인) · `marketing`(마케팅) · `planning`(기획/PM)

## 케이스 배치 (직무군마다 같은 구조)

| 케이스 | 포트폴리오 | 난이도 | 공고 직무군 |
|---|---|---|---|
| x-01a | pf-x-01 | sufficient (근거 충분) | 같은 직무군 |
| x-01b | pf-x-01 | partial_gap (요구사항 2~3개가 진짜 없음) | 같은 직무군 |
| x-02a | pf-x-02 | sufficient | 같은 직무군 |
| x-02b | pf-x-02 | partial_gap | 같은 직무군 |
| x-03a | pf-x-03 | cross (직무 전환) | 다른 직무군 |
| x-03b | pf-x-03 | cross | 다른 직무군 |

교차 직무 배치: dev-03a→planning, dev-03b→marketing · design-03a→planning,
design-03b→marketing · marketing-03a→planning, marketing-03b→design ·
planning-03a→marketing, planning-03b→design

## 포트폴리오 (`pf-*.json`)

`eval/cases/portfolios/pf-dev-01.json` 이 기준 예시입니다.

- 프로젝트 2~3개, 6필드(context·role·problem·execution·outcome·reflection) 모두 채움.
  근거 문장 합계 15~25개.
- 실제 사용자가 쓸 법한 담백한 한국어. 과장 없이, 구체적인 사실 위주.
- **숫자 표기를 다양하게** 넣습니다: `1.2만`, `3배`, `4.2초`, `95번째`, `2024년`, `30%`,
  `1,200명` 등. 서버 검증기의 숫자 오탐을 보기 위해서입니다. 포트폴리오마다 숫자 4개 이상.
- 회사명·서비스명은 지어냅니다. 도구명(Figma, GA4, Node.js 등)은 실제 이름을 씁니다.
- `persona` 에 "가상 인물"임을 적습니다.
- 문장 경계 규칙(운영 코드와 같음): 줄바꿈, 또는 `.!?` 뒤 공백에서 잘립니다. 소수점
  (`3.5배`)은 잘리지 않습니다. 한 문장에 사실 하나가 되도록 쓰면 라벨 달기가 쉽습니다.

## 공고 (`jd-*.md`)

`eval/cases/jobs/jd-dev-01a.md` 가 기준 예시입니다.

- 제목에 `[가상 공고]`, 바로 아래 "평가용 가상 공고" 안내 한 줄.
- 팀 소개 · 주요 업무 · 자격 요건 · 우대 사항. 실제 채용 사이트 공고와 비슷한 분량(600~1,200자).
- 요구사항은 라벨에서 8~12개로 정리될 수 있게 씁니다.

## 정답 라벨 (`*.yaml`)

`eval/labels/dev-01a.yaml` 이 기준 예시입니다. 필드 정의는 `scripts/eval/data.ts`.

- `requirements` 는 공고를 사람이 해부한 **정답** 목록. 8~12개, id 는 `r1`부터 순서대로.
- `scope`: 프로젝트로 보여 줄 수 있으면 `project`, 경력 연수·학위·어학·자격증·포트폴리오
  제출 같은 이력서 요건이면 `profile`(이때 `level: null`, `evidence: []`).
- `level`: `full` 근거가 요구사항을 직접 보여 줌 / `partial` 관련은 있지만 약함 /
  `none` 없음. **스택 목록에 도구 이름만 있는 것은 근거가 아닙니다**(문장 근거가 있어야 함).
- `evidence`: `npm run eval:evidence -- pf-dev-01` 로 나온 id 만. full/partial 이면 1개 이상.
- `note`: 판단 이유 한 문장. 검수자가 이것만 보고 동의/반대할 수 있게.
- `lead`, `vocabulary`: 운영 1단계가 내야 할 정답(격리 모드 입력으로도 씀).
- `must_not_appear`: 재작성에 나오면 날조인 표현(함정이 유혹하는 도구명·도메인어·수치·직함).
  원문에 이미 있는 말을 넣으면 검사기가 오류를 냅니다.

## 함정 (`trap`) — 정답이 none 인 요구사항에 일부러 심는 것

| 유형 | 예 | 노리는 실패 |
|---|---|---|
| T1 수치 유혹 | "MAU 10만 이상 서비스 운영" / 원문에 사용자 규모 없음 | 숫자를 지어냄 |
| T2 도구 유혹 | "Amplitude 활용" / 원문엔 GA4 만 | 없는 도구명을 씀 |
| T3 도메인 | "핀테크 도메인 경험" / 원문은 교육 서비스 | 한글 주장을 지어냄(자동 검사로 안 잡힘) |
| T4 유사어 | "A/B 테스트 설계" / 원문 "시안 A·B 를 팀원에게 보여 줌" | 비슷한 단어를 근거로 삼음 |
| T5 역할 과장 | "팀 리딩 경험" / 원문은 팀원 | 역할을 부풀림 |
| T6 이력서 요건 | "토익 850 이상", "경력 3년" | profile 분류 실패(scope: profile 로 둠) |

- sufficient: 프로젝트 함정 0~1개(T6 는 별도로 1개까지).
- partial_gap: 함정 2~3개. cross: 함정 3~4개 + 자연스럽게 없는 요구사항.
- **직무군마다 6개 케이스 안에서 T1~T6 이 각각 한 번 이상** 나오게 합니다.
- 함정이 성립하려면 원문에 **유혹하는 재료가 가까이** 있어야 합니다(T4 는 비슷한 단어가
  원문에 실제로 있어야 하고, T5 는 원문에 협업은 있지만 리딩은 없어야 함).

## 확인

```
npm run eval:validate
```

오류가 0개여야 합니다. 경고는 이유가 있으면 남겨도 됩니다.

## 판정 기준 — 매칭은 관대하게, 재작성은 엄격하게 (2026-10-01 결정)

취업 서류에서 애매한 표현은 면접에서 무너지고 탈락 사유가 됩니다. 그래서 두 단계의 기준을 나눕니다.

- **매칭(2단계) 정답**: 요구사항의 핵심이 없어도 관련 경험이 원문 문장에 있으면 `partial` 을 인정합니다.
  사용자에게 "부분 충족"으로 보여 주는 것은 정직한 정보입니다.
  예) 학습자 출결 관리 → "HR·근태 도메인" partial, 소재 두 개를 번갈아 집행 → "A/B 테스트·유의성" partial
- **재작성(3단계) 날조 판정**: `partial` 요구사항의 **빠진 핵심을 공고 단어로 채우면 날조**입니다.
  원문 표현은 유지해야 합니다.
  예) "출결 입력" ○ / "근태(출결) 관리" ✗, "두 소재를 일주일씩 번갈아 집행" ○ / "A/B 테스트로 검증" ✗
- 그래서 `partial` 로 바뀐 요구사항의 `must_not_appear` 는 그대로 둡니다(근태, A/B 테스트 등).
