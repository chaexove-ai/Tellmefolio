# 직무 전환 재구성 — 설계

> 2026-09-21 작성. 아직 구현 전이며, 현재 `/job-switch` 화면은 100% 목업입니다
> (`mockData` + `setTimeout(1200)`).

## 1. 경쟁 기준선

이 기능의 경쟁 상대는 다른 포트폴리오 서비스가 아니라 **사용자가 ChatGPT에
포트폴리오와 채용 공고를 붙여넣는 것**입니다. 그 결과물은 꽤 좋습니다.

그러니 **문장력으로 이기려 하지 않습니다.** 같은 모델을 쓰기 때문에 이길 수
없는 싸움입니다. 이길 수 있는 자리는 네 곳입니다.

| 축 | 채팅이 못 하는 이유 |
|---|---|
| **재료** | 채팅에 붙여넣는 사람은 경험을 요약해서 넣고, 모델은 빈칸을 상상으로 채웁니다. 우리는 프로젝트별 6필드·README·언어 구성을 구조화해 갖고 있습니다 |
| **날조 차단** | 채팅은 근거가 없어도 "전환율 30% 개선"을 씁니다. 취업 문서에서 지어낸 수치는 면접에서 무너집니다 |
| **공고 해부** | 채팅은 요구사항을 전부 "채워"줍니다. 지어내서라도. 우리는 **무엇이 진짜 없는지** 알려줍니다 |
| **검토 가능성** | 채팅은 새 글 한 덩어리를 줍니다. 무엇이 왜 바뀌었는지 모르니 검토할 수 없습니다 |

핵심 한 줄: **"안심하고 제출할 수 있는 문서"** 가 파는 것이지, 좋은 문장이
아닙니다.

## 2. 파이프라인

한 번의 프롬프트로는 위 2·3번이 성립하지 않습니다. 네 단계로 나눕니다.

### 0단계 — 근거 단위 쪼개기 (서버, LLM 없음)

포트폴리오를 읽어 각 프로젝트의 6필드를 **문장 단위 근거(evidence)** 로
쪼개고 id를 붙입니다.

```
p{projectId}:{field}:{sentenceIndex}
예) 7f3a:execution:2
```

이 id가 이후 모든 추적의 기반입니다. 재작성된 문장은 반드시 이 id 중
하나를 가리켜야 합니다.

### 1단계 — 공고 해부 (LLM 1회)

입력은 공고 원문입니다. URL이면 서버가 가져옵니다 —
`generate-draft` 의 `isSafeUrl`(루프백·사설망·메타데이터 차단)을 그대로
재사용합니다. 가져오기에 실패하면 조용히 넘어가지 말고 붙여넣기를 유도합니다.

```json
{
  "role": "프로덕트 매니저",
  "requirements": [
    { "id": "r1", "text": "데이터 기반 의사결정 경험",
      "kind": "must", "keywords": ["지표", "A/B", "가설"] }
  ],
  "vocabulary": ["그로스", "리텐션", "온보딩"]
}
```

- `kind` 는 `must` / `nice`. 강조 순서를 정하는 데 씁니다.
- 요구사항은 **8~12개로 제한**합니다. 더 많으면 표가 읽히지 않습니다.
- `vocabulary` 는 그 공고가 실제로 쓰는 어휘입니다. 3단계에서 같은 사실을
  그 업계 말로 옮기는 데 씁니다.

### 2단계 — 근거 매칭 (LLM 1회)

입력은 요구사항 목록과 0단계의 근거 목록(id + 문장)입니다.

```json
{
  "matches": [
    { "requirementId": "r1", "level": "full",
      "evidenceIds": ["7f3a:outcome:0", "7f3a:execution:2"],
      "why": "A/B 테스트 설계와 지표 정의가 실행·성과에 모두 있습니다" }
  ]
}
```

**기계적 방어 장치**: `evidenceIds` 는 입력에 있던 id 만 허용합니다. 서버가
대조해서 존재하지 않는 id 는 버리고, 근거가 하나도 남지 않으면 그 항목의
`level` 을 `none` 으로 강등합니다. 모델이 근거를 지어내도 표에는 "근거 없음"
으로 나옵니다.

`level: "none"` 인 항목이 곧 화면의 **부족한 부분(gaps)** 입니다.

### 3단계 — 재작성 (LLM 1회, 프로젝트가 많으면 분할)

입력은 원본 프로젝트, 2단계 매칭 결과, 공고 어휘입니다.

프롬프트가 지켜야 할 규칙:

- **사실을 더하지 않습니다.** 어휘와 강조 순서만 바꿉니다.
- **수치는 원본에 있는 것만.** 새 숫자를 만들지 않습니다.
- `level: "none"` 인 요구사항은 **채우지 않습니다.** gap 으로 남깁니다.
- 출력하는 문장마다 어느 근거에서 나왔는지 id 를 답니다.

같은 사실을 직무 언어로 옮기는 예:

> 원본: "예약 전환율을 개선했습니다"
> 개발자 공고: "전환 퍼널에 이벤트 로깅을 붙이고 A/B 테스트로 검증했습니다"
> PM 공고: "가설을 세우고 지표를 정의해 개선 여부를 판단했습니다"

사실은 하나이고 말이 다릅니다. 이게 "재구성"이지, 새로 쓰는 것이 아닙니다.

### 4단계 — 검증 (서버, LLM 없음)

**LLM 에게 자기 검증을 시키지 않습니다.** 같은 모델은 같은 착각을 반복하고,
호출만 한 번 더 듭니다. 기계적으로 대조하는 편이 싸고 확실합니다.

| 검사 | 방법 |
|---|---|
| 숫자 | 출력에 등장하는 숫자 토큰이 원본 근거에 있는가 |
| 근거 id | 실재하는 id 인가 |
| 고유명사 | 출력의 기술명·제품명이 원본에 있는가(느슨하게) |

걸린 문장은 화면에 경고로 표시하고 **원본 문장을 나란히 보여줍니다.** 지우지
않는 이유는, 오탐일 수 있고 판단은 사용자 몫이기 때문입니다.

## 3. 데이터 구조

```sql
job_switch_runs (
  id uuid pk,
  portfolio_id uuid references portfolios on delete cascade,
  user_id uuid references auth.users on delete cascade,
  target_job text,
  jd_url text, jd_text text,
  requirements jsonb,   -- 1단계
  matches jsonb,        -- 2단계
  flags jsonb,          -- 4단계
  created_at timestamptz
)

job_switch_projects (   -- 3단계 결과
  id uuid pk,
  run_id uuid references job_switch_runs on delete cascade,
  source_project_id uuid,
  position int,
  name, role, context, problem, execution, outcome, reflection text,
  stack text[],
  evidence jsonb        -- 필드별 근거 id 목록
)
```

**왜 `portfolios` 에 바로 쓰지 않는가**: 재구성본은 원본을 대체하지 않습니다.
원본 하나에서 직무별로 여러 개가 나오고, 원본은 그대로 남아야 합니다.
사용자가 "이대로 저장"을 눌렀을 때만 새 `portfolios` 행으로 복사합니다.

RLS 는 기존과 같은 방식 — `user_id = auth.uid()`.

## 4. 화면

요청 화면은 지금 구조를 그대로 씁니다(포트폴리오 선택 + 목표 직무 + 공고).

결과 화면은 세 구역입니다. **커버리지 표를 맨 위에 둡니다** — 이게 이 기능의
정체성이고, 재구성된 글보다 먼저 봐야 하는 정보입니다.

1. **커버리지 표** — 요구사항 × 충족도. 충족이면 근거 문장을 펼쳐 보여주고,
   근거 없음은 눈에 띄게 표시합니다.
2. **문장 diff** — 원본 → 변경본, 그리고 "이 공고의 어느 요구사항 때문인지".
3. **경고** — 4단계에서 걸린 문장과 원본 병기.

하단에 `이대로 새 포트폴리오로 저장` / `버리기`.

## 5. 비용과 제약

- LLM 호출 3회. 1단계는 Haiku 로 충분하고, **2·3단계는 체급을 탑니다** —
  근거 추적과 날조 억제가 작은 모델에서 먼저 무너집니다. 이 두 호출만 상위
  모델로 올리는 결정이 필요합니다(Edge Function 의 `MODEL` 시크릿을 단계별로
  나눠야 합니다).
- Edge Function 은 첫 응답까지 150초입니다. 프로젝트 5개 기준 40~70초로
  예상하지만, 프로젝트가 많으면 3단계를 프로젝트별로 쪼개 병렬 호출합니다.
- 사용량 차감은 **사용자 눈에 1회**여야 합니다. 내부 호출이 3회라는 건 우리
  사정입니다. `draft_generations` 에 `kind` 컬럼(`draft` / `job_switch`)을
  더해 구분합니다.

## 6. 만들지 않을 것

- **채용 공고 자동 크롤링.** 사이트마다 구조가 다르고 대부분 막습니다. URL 은
  시도하되 실패하면 붙여넣기로 유도합니다.
- **"이 공고에 지원할 만한가" 같은 조언.** 우리가 판단할 근거가 없습니다.
- **자기소개서 생성.** 별개 제품입니다.

## 7. 검증 방법

만든 뒤에 실제 공고 3개와 실제 포트폴리오로 돌려서 **ChatGPT 결과와 나란히
놓고 비교합니다.** 평가 기준은 문장이 예쁜가가 아니라 두 가지입니다.

1. 원본에 없는 수치·사실이 몇 개 들어갔는가 (적을수록 좋음)
2. "근거 없음"으로 짚은 항목이 실제로 없는 것이었는가

이 두 개에서 이기지 못하면 이 기능은 만들 이유가 없습니다.

## 8. 선행 조건

직무 전환은 원본 포트폴리오를 재료로 씁니다. 재료가 빈약하면 결과도
빈약합니다. 순서상 먼저 끝나야 할 것:

- 프로젝트별 이미지 (재구성 시 함께 옮겨야 함)
- AI 사용 횟수 제한 (화면의 3/5회가 아직 가짜)
