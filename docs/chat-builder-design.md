# 대화로 만들기 — 설계

> 2026-09-25 작성. 아직 구현 전입니다.
> 화면 예시: `docs/mockups/chat-builder.html` (브라우저로 열면 눌러볼 수 있습니다)

## 1. 한 줄

**겉은 챗봇, 속은 인터뷰.** 홈 맨 위의 입력창에 프로젝트 이야기를 편하게
쓰면, AI가 질문을 이어가며 케이스 스터디 칸을 채웁니다. AI는 글을 대신
쓰지 않고 **묻습니다.** 초안의 모든 문장은 "몇 번째 답에서 왔는지"로
추적됩니다.

서비스 이름이 Tellmefolio 이고 한 줄 소개가 "이야기하면 포트폴리오가
됩니다"인데, 지금은 정작 이야기하는 기능이 없습니다. 이 기능이 그 약속을
화면으로 만듭니다.

## 2. 결정 기록

### 왜 "네 번째 자료"가 아니라 챗봇 입구인가

처음 안은 위저드의 자료 입력(저장소·링크·메모) 옆에 "AI 인터뷰"를 하나 더
두는 것이었습니다. 사용자가 **검색창처럼 홈에 두자**고 했고 그쪽을
택했습니다. 자료 목록 네 번째 칸에 두면 서비스의 핵심 경험이 선택지 하나로
숨습니다. 입력창 하나로 시작하면 "이야기로 시작한다"가 첫 화면에서 보입니다.

### 왜 "대화로 생성"이 아니라 "대화로 인터뷰"인가

- **ChatGPT와 같은 싸움을 하지 않습니다.** 대화하며 글을 써주는 건 사용자가
  이미 ChatGPT에서 할 수 있습니다. `job-switch-design.md` 1절과 같은 이유로,
  문장력으로 이기려 하지 않습니다.
- **날조를 막을 수 있어야 합니다.** 대화 흐름 속에서 AI가 살을 붙이기
  시작하면 걸러낼 방법이 없습니다. 인터뷰로 받은 답은 "사용자가 직접 말한
  문장"이라, 직무 전환의 근거 id 방식을 그대로 쓸 수 있습니다.
- **편집기와 역할이 겹치지 않게 합니다.** 대화는 재료를 모으는 곳이고,
  문장을 다듬는 곳은 편집기입니다. 대화로 수정까지 하게 하면 "어디서
  고쳐야 하지?"가 생깁니다.

### 아직 사용자 확인이 필요한 것 (기본값으로 설계함)

| 질문 | 기본값 | 이유 |
|---|---|---|
| 홈의 "새 포트폴리오 만들기"를 대신하나, 하나 더 두나 | **하나 더.** 입력창이 주 입구, 기존 위저드는 "저장소로 시작하기" 링크로 남김 | 저장소가 많은 개발자에게는 위저드가 더 빠릅니다 |
| 입력창을 홈에만 두나, 어디서든 부르나 | **1차는 홈에만** | 어디서든 부르려면 2차의 "명령" 기능이 먼저 있어야 의미가 있습니다 |

## 3. 흐름

```
홈 입력창 ─→ 대화 화면 ─→ (칸 4개 이상) 초안 만들기 ─→ 편집기
            [채팅 | 채워지는 칸]
```

1. **첫 문장 해석.** "작년에 한 미용실 예약 앱 리뉴얼 정리하고 싶어" →
   프로젝트 이름 후보를 뽑아 대화 제목으로 씁니다. 링크가 있으면 감지해
   알려줍니다(깃허브 링크면 README를 재료로 붙임, 2차).
2. **질문 루프.** 비어 있는 칸을 순서대로 겨냥합니다: 맥락 → 역할 → 문제 →
   실행 → 성과 → 배운 점.
   - 답이 모호하면 **그 칸에 한해 한 번만** 되묻습니다. 예: "올랐어요" →
     "얼마나요? 정확하지 않으면 넘어가도 돼요 — 지어서 쓰진 않을게요."
   - "넘어가기"는 언제나 됩니다. 넘긴 칸은 "건너뜀"으로 남고, 초안에서
     비워 둡니다.
   - 한 답이 여러 칸을 채우면(예: 문제와 실행을 한 번에 말함) 둘 다 표시하고
     그 칸은 다시 묻지 않습니다.
3. **초안 만들기.** 칸이 4개 이상 차면 버튼이 나옵니다. 답변만으로 6필드를
   씁니다. 문장마다 근거 답변 id를 답니다.
4. **편집기로.** 새 포트폴리오(또는 고른 기존 포트폴리오의 새 프로젝트)로
   저장하고 편집기를 엽니다.

한 대화 = 한 프로젝트입니다. 대화 끝에 "다른 프로젝트도 이야기하기"로 같은
포트폴리오에 이어 붙입니다. 여러 프로젝트를 한 대화에 섞으면 어느 답이 어느
프로젝트 것인지 흐려집니다.

## 4. 날조 방지 — 직무 전환과 같은 장치

- 사용자 답변을 문장 단위로 쪼개 id를 붙입니다: `a{답변 순번}:{문장 순번}`.
  (`job-switch/logic.ts` 의 `splitSentences` 를 그대로 씁니다)
- 오른쪽 칸에 보이는 요약도, 초안 문장도 이 id를 **반드시** 답니다. 없는 id는
  서버가 버립니다.
- 초안에 대해 4단계 기계 검증을 그대로 돌립니다: 답변 어디에도 없는 숫자·
  영문 이름, 근거 없는 문장 → "확인 필요".
- 공유 방법: `logic.ts` 를 `supabase/functions/_shared/evidence.ts` 로 옮기고
  두 함수가 같이 씁니다. 옮기면서 `job-switch` 도 한 번 다시 배포합니다.

## 5. 데이터

```sql
interview_sessions (
  id uuid pk,
  user_id uuid references auth.users on delete cascade,
  portfolio_id uuid references portfolios on delete set null, -- 저장 후 연결
  project_id uuid references portfolio_projects on delete set null,
  title text,                       -- 첫 문장에서 뽑은 프로젝트 이름
  status text,                      -- 'open' | 'drafted' | 'abandoned'
  fields jsonb,                     -- { outcome: { state: 'filled'|'skipped', summary, answerIds[] }, ... }
  created_at, updated_at
)

interview_messages (
  id uuid pk,
  session_id uuid references interview_sessions on delete cascade,
  position int,
  role text,                        -- 'ai' | 'user'
  text text,
  target_field text,                -- ai 질문이 겨냥한 칸
  follow_up boolean,                -- 되묻기였는지
  created_at
)
```

RLS 는 기존과 같이 본인 것만. 대화가 중간에 끊겨도 `open` 세션으로 남아
홈의 "지난 포트폴리오 이어서"에서 다시 엽니다.

## 6. Edge Function `interview`

한 턴에 한 번 부릅니다. 모델은 Haiku(`INTERVIEW_MODEL`, 기본
`claude-haiku-4-5-20251001`) — 질문 만들기와 칸 분류는 가벼운 일입니다.

입력: 세션 id + 방금 사용자 답변. 서버가 DB에서 칸 상태와 **최근 6턴만**
읽어 프롬프트에 넣습니다(대화가 길어질수록 비용이 쌓이는 것을 막음).

출력 JSON:

```json
{
  "fills": [{ "field": "problem", "summary": "…", "answerIds": ["a3:0"] }],
  "skip": null,
  "next": { "field": "execution", "question": "…", "followUp": false },
  "done": false
}
```

서버가 하는 일: `answerIds` 대조, 되묻기가 칸당 1회를 넘으면 강제로 다음
칸으로, 전체 질문 12개에서 끊고 "초안 만들기"로 유도.

초안 만들기는 별도 호출(`interview-draft` 또는 같은 함수의 `mode: "draft"`).
직무 전환의 3단계와 같은 규칙의 프롬프트, 모델은 Sonnet
(`JOB_SWITCH_STRONG_MODEL` 과 같은 값을 씀).

## 7. 화면

예시 파일(`docs/mockups/chat-builder.html`)이 기준입니다.

- **홈**: 가운데 큰 제목 "어떤 프로젝트 이야기를 해볼까요?" + 입력창 +
  바로가기 칩 3개(깃허브 링크로 시작 / 공고에 맞춰 다시 쓰기 / 지난 포트폴리오
  이어서) + 아래 내 서재.
- **대화**: 왼쪽 채팅, 오른쪽 칸 6개와 진행 막대. 답하면 "✓ ○○에 저장"
  표시가 붙고 오른쪽 칸이 채워지며 "답변 n에서"가 남습니다.
- 줄글 안내를 늘어놓지 않습니다. 사용자가 봐야 할 것은 "지금 무엇을 묻는지"와
  "얼마나 찼는지" 둘입니다.
- 데스크탑 전용 게이트(1200px) 안쪽입니다.

## 8. 만들지 않을 것

- **포트폴리오와 무관한 질문에 답하기.** "자기소개서 써줘", "면접 질문 알려줘"
  → 정중히 범위 밖이라고 답합니다. 아무거나 답하면 비용도 늘고 서비스
  정체성도 흐려집니다.
- **대화로 편집하기.** 문장 다듬기는 편집기에서.
- **음성 입력.** 나중 일입니다.

## 9. 2차 — 명령 입구

같은 입력창에서 "이 포폴 PM 공고에 맞게 바꿔줘" → 직무 전환, "영어로
뽑아줘" → 내보내기로 연결합니다. 이미 있는 기능을 부르는 입구입니다. 1차에
넣지 않는 이유: 의도 분류가 틀리면 엉뚱한 화면으로 보내게 되고, 그 실패가
인터뷰 자체의 인상까지 깎습니다.

## 10. 비용과 제약

- 턴당 Haiku 1회 + 초안 Sonnet 1회. 질문 12개 상한이면 한 프로젝트에 모델
  호출 최대 13회.
- 사용량은 초안 만들기 때 `draft_generations` 한 줄(대화 턴 토큰 합산).

## 11. 검증 방법

실제 사용자 5명(부트캠프 동기, 디자이너 포함)에게 프로젝트 하나씩 대화로
만들어 보게 하고 봅니다.

1. 끝까지 가는 비율 — 중간에 그만두는 칸이 어디인가
2. 초안의 "확인 필요" 수 — 0에 가까워야 함
3. 같은 사람이 빈 칸 위저드로 쓴 것과 비교해 성과 칸에 숫자가 더 들어갔는가
   (되묻기가 제 몫을 하는지)
