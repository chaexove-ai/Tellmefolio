# 편집 화면 재설계 — 정형화를 깨되 품질은 지킨다

작성 2026-09-22 · 대상 `src/pages/wizard/PortfolioEditor.tsx` (880줄), `src/components/portfolio-templates/*`

---

## 1. 무엇이 문제인가

사용자의 말: *"여전히 복잡하고 포폴을 정형화 하는느낌"*. 화면을 보면 원인이 셋입니다.

**다섯 칸이 과제 목록으로 읽힙니다.** 1~5 번호가 붙어 있고, 빈 칸마다
`예: 신규 사용자가 첫 화면에서 다음 단계로 넘어가지 못하고 있었습니다`
같은 예시가 떠 있습니다. 번호는 "순서"가 아니라 "해야 할 일"로 읽히고,
예시 문장은 사람들을 그 문장에 맞춰 쓰게 만듭니다. 결과적으로 누가 써도
같은 다섯 단락이 나옵니다.

**프로젝트 10개가 전부 같은 무게입니다.** 알약이 한 줄로 늘어서 있고
"제목 없음"이 3개 섞여 있습니다. 실제 포트폴리오는 대표작 2~3개가 깊고
나머지는 얕은데, 지금 UI에는 그 차이를 표현할 방법이 없습니다. 그래서
10개를 다 깊게 써야 할 것 같은 압박이 생깁니다.

**입력 폼으로 읽힙니다.** 라벨 + 안내문 + placeholder + "직접 입력" 배지가
칸마다 붙어 있습니다. 글 쓰는 자리가 아니라 양식 채우는 자리입니다.

## 2. 자유 캔버스를 쓰지 않는 이유 (결정 기록)

피그마·미리캔버스식 자유 배치가 두 번 검토됐고 두 번 접혔습니다. 세 번째로
다시 나올 때를 위해 이유를 남깁니다.

| 깨지는 것 | 왜 |
|---|---|
| 템플릿 4종 · 여백 · 나열 · 서체 | 전부 "알아서 배치해주는" 장치입니다. 손으로 놓기 시작하면 할 일이 없어집니다 |
| 한/영 전환 | 영어는 글자 수가 20~30% 늘어납니다. 템플릿은 다시 흐르지만 고정 박스는 넘칩니다 |
| 직무 전환 재구성 | 내용을 다시 써서 넣는 기능입니다. 위치가 고정되면 새 내용이 들어갈 자리가 없습니다 |
| 공개 링크의 모바일 | `/p/:id` 는 폰에서 열립니다. 1200px 절대 좌표는 다시 흐르지 않습니다 |
| PDF 내보내기 | 지금은 템플릿을 그대로 캡처하면 됩니다. 자유 배치는 페이지 나눔을 직접 계산해야 합니다 |

그리고 품질이 내려갑니다. 이 서비스의 약속은 **"쉽게 만드는데 결과물이
좋다"** 입니다. 자유 캔버스는 품질 책임을 사용자에게 넘깁니다. 대부분은
템플릿보다 못한 배치를 만들고, 그 결과물이 채용 담당자에게 갑니다.

**대신 블록 단위 편집을 씁니다** (4절). 노션·프레이머 방식입니다. 자유롭게
느껴지지만 다시 흐르기 때문에 위 다섯 가지가 전부 살아 있습니다.

> **[2026-09-22 갱신]** 이 결론은 유효하지만 불충분했습니다. 템플릿만으로는
> 취향을 담을 수 없어 사람들이 안 쓸 거라는 지적이 있었고, 맞는 말입니다.
> 자유 배치를 **블록 하나 안에 가두면** 위 표의 다섯 가지가 전부 살아난
> 채로 자유도를 열 수 있습니다 — `docs/editor-freedom.md` 참고.

## 3. 프로젝트마다 깊이 선택

### 3.1 두 가지 깊이

| | 간단히 (`brief`) | 케이스 스터디 (`full`) |
|---|---|---|
| 보이는 것 | 제목 · 한 줄 설명 · 이미지 · 스택 | 지금의 5필드 전부 + 이미지 |
| 쓰는 데 | 1분 | 15분 |
| 쓰임새 | 이미지로 보여주는 작업물, 참여도가 낮은 프로젝트 | 대표작 2~3개 |

10개 중 3개는 `full`, 7개는 `brief` — 이게 실제 포트폴리오의 모양입니다.

### 3.2 데이터

```sql
alter table public.portfolio_projects
  add column if not exists depth text not null default 'full'
  check (depth in ('brief', 'full'));
```

기본값이 `full` 인 이유: 기존 프로젝트가 이 마이그레이션 때문에 내용이
사라진 것처럼 보이면 안 됩니다. 지금 보이는 모양이 그대로 유지됩니다.

### 3.3 전환은 손실이 없어야 합니다

`full` → `brief` 로 바꿔도 **문제·실행·성과·회고 값은 DB에 그대로 둡니다.**
화면에서 안 그릴 뿐입니다. 다시 `full` 로 바꾸면 쓰던 글이 돌아옵니다.
이 규칙을 깨면 사용자가 깊이를 바꾸는 것 자체를 두려워하게 됩니다.

`brief` 의 "한 줄 설명"은 **새 컬럼을 만들지 않고 기존 `context` 를 씁니다.**
라벨만 "맥락 및 배경" → "한 줄 설명"으로 바뀝니다. 두 모드가 같은 칸을
공유하므로 전환해도 다시 쓸 일이 없습니다.

### 3.4 화면

- 프로젝트 개요 카드 상단에 세그먼트 두 개 (`간단히` / `케이스 스터디`)
- `brief` 일 때 5칸 중 1번만 남고 나머지는 접힘 — 삭제가 아니라 접힘이라는
  것이 보여야 합니다. 접힌 자리에 "케이스 스터디로 바꾸면 다시 보입니다"
- 탭 알약에 깊이 표시(작은 점 하나). 10개 중 어느 것이 대표작인지 한눈에

### 3.5 템플릿

4개 템플릿 전부 `brief` 를 그릴 수 있어야 합니다. `brief` 는 제목 + 한 줄 +
이미지라 오히려 단순합니다. 주의할 곳은 매거진형 — 이미지가 주인공인
템플릿이라 `brief` 와 가장 잘 맞고, 여기서 먼저 확인합니다.

## 4. 프로젝트별 이미지

### 4.1 데이터

```sql
create table if not exists public.portfolio_project_images (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references public.portfolio_projects(id) on delete cascade,
  storage_path text not null,
  caption text not null default '',
  position int not null default 0,
  created_at timestamptz not null default now()
);
```

RLS 는 `portfolio_projects` 와 같은 방식 — 그 프로젝트가 속한 포트폴리오의
`user_id = auth.uid()` 일 때 쓰기, `visibility='public'` 이면 읽기.

### 4.2 Storage

**새 버킷을 만들지 않고 `portfolio-covers` 를 그대로 씁니다.** 기존 정책이
`(storage.foldername(name))[1] = auth.uid()::text` 라, 경로만 맞추면 정책을
새로 쓸 필요가 없습니다.

```
{userId}/{portfolioId}/projects/{projectId}/{n}.webp
```

버킷 이름이 내용과 어긋나는 것은 감수합니다 — 정책을 한 벌 더 관리하는
비용보다 낫습니다. (버킷 이름은 바꿀 수 없으므로 주석으로 남깁니다.)

### 4.3 규칙

- 프로젝트당 **최대 8장**. 그 이상은 포트폴리오가 아니라 갤러리입니다
- 업로드 전 `lib/images.ts` 의 `shrinkImage` 를 반드시 통과 (긴 변 1600px,
  WebP). 8장 × 4MB 가 그대로 올라가면 공개 링크가 폰에서 안 열립니다
- 순서는 끌어서 바꿉니다 (`position`)
- 캡션은 선택. 비면 아예 안 그립니다
- 프로젝트 삭제 시 이미지 행은 cascade 로 지워지지만 **Storage 파일은
  따로 지워야 합니다** — 표지에서 겪은 것과 같은 함정입니다

### 4.4 화면

프로젝트 개요 카드 안, 스택 태그 아래. 썸네일 줄 + "이미지 추가".
`brief` 모드에서는 이 영역이 카드의 주인공이 되도록 위로 올라갑니다.

## 5. 미리보기 확대 보기

지금 미리보기는 오른쪽 칼럼에 `zoom = min(1.5, 폭/720)` 으로 눌려 있습니다.
글을 고치면서 보기엔 맞지만, **"내보내면 이렇게 나온다"를 확인하기엔
작습니다.**

- 미리보기 헤더에 확대 버튼 → 전체화면 오버레이
- 안에서 `100% / 화면맞춤` 전환, ESC 로 닫기
- 같은 `PortfolioRenderer` 를 씁니다. 별도 뷰를 만들면 내보내기와
  어긋나는 순간이 옵니다 (Export 화면에서 이미 한 번 겪었습니다)

## 6. 블록 편집 — 미리보기에서 직접

### 6.1 블록이란

| 블록 | 단위 |
|---|---|
| 프로젝트 | 1개 = 1블록 |
| 필드 | 맥락/문제/실행/성과/회고 각각 |
| 이미지 | 1장 = 1블록 |

### 6.2 할 수 있는 것 (순서대로 구현)

1. **순서 바꾸기** — 프로젝트를 끌어서 위아래로. `position` 컬럼이 이미
   있어서 데이터는 준비돼 있습니다
2. **숨기기** — 이 프로젝트에선 "배운 점"을 안 보이게.
   `portfolio_projects.hidden_fields text[] default '{}'`
3. **폭 고르기** — 전체폭 / 반폭. `span text default 'full'`
4. **이미지 크기** — 작게 / 크게 / 전체폭
5. **그 자리에서 글자 고치기** — 미리보기의 문단을 눌러 바로 수정.
   왼쪽 폼과 같은 값을 씁니다 (별도 저장 경로를 만들지 않습니다)

1~4 는 값 하나씩이라 안전합니다. 5는 `contentEditable` 과 상태 동기화가
얽혀서 난이도가 다릅니다 — **5는 반드시 마지막에, 앞이 안정된 뒤에.**

### 6.3 폼의 역할 축소

블록 편집이 들어오면 왼쪽 폼은 **"처음 채울 때"** 만 쓰게 됩니다. 그때
번호와 예시 문장을 걷어내고, 빈 칸은 기본으로 접습니다. 복잡하다고 느낀
그 밀도가 자연스럽게 내려갑니다.

## 7. 깨뜨리면 안 되는 것

각 단계 끝에 이 넷을 확인합니다. 하나라도 깨지면 그 단계는 끝난 게
아닙니다.

- [ ] **한/영 전환** — 영어로 바꿔도 넘치거나 겹치지 않는다
- [ ] **PDF 내보내기** — 미리보기와 파일이 같다
- [ ] **공개 링크 모바일** — `/p/:id` 를 폰에서 열어 읽을 수 있다
- [ ] **직무 전환** — 내용이 새로 들어와도 레이아웃이 받아준다

## 8. 구현 순서

각 단계는 **거기서 멈춰도 쓸 수 있는 상태**로 끝냅니다.

| 단계 | 내용 | 마이그레이션 |
|---|---|---|
| 1 | 깊이 선택 (`depth`) + 템플릿 4종 대응 | `depth` 컬럼 |
| 2 | 프로젝트별 이미지 (업로드·순서·삭제) | `portfolio_project_images` 테이블 |
| 3 | 미리보기 확대 보기 | 없음 |
| 4 | 블록 편집 6.2 의 1~4 | `hidden_fields`, `span` |
| 5 | 폼 정리 (번호·예시 제거, 빈 칸 접기) | 없음 |
| 6 | 인라인 텍스트 편집 | 없음 |

1과 2는 함께 갑니다 — `brief` 모드는 이미지가 주인공이라 이미지 없이는
반쪽입니다.

마이그레이션 파일명은 **14자리**(`YYYYMMDDHHMMSS`)로 짓습니다. 8자리로
지으면 같은 날 두 번째 파일에서 버전이 겹쳐 막힙니다 (CONTEXT.md 참고).
