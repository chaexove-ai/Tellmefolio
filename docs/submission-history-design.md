# 제출 기록 — 설계

> 2026-09-25 작성. 아직 구현 전입니다.
> 지금의 "버전 관리"(`/library/portfolios/:id/versions`, 100% 목업)를 대체합니다.

## 1. 한 줄

**내보낼 때 "어디에 제출하나요?"를 한 칸 받고, 그 순간의 결과물을 그대로
남깁니다.** 버전 목록이 곧 지원 기록이 됩니다.

면접 전날 "A사에 낸 포트폴리오가 어떤 버전이었지?"를 다시 볼 수 있어야
합니다. 그 사이에 편집기에서 계속 고쳤다면 지금 화면은 제출한 것과 다릅니다.

## 2. 결정 기록 — 왜 일반 버전 관리가 아닌가

| 일반 버전 관리 (아무 때나 저장·되돌리기) | 제출 기록 |
|---|---|
| 되돌리기가 필요한 순간이 드뭅니다. 직무 전환은 이미 원본을 두고 새 포트폴리오를 만들고, 편집기는 덮어쓰는 방식입니다 | 취업 준비에서 실제로 생기는 질문("무엇을 냈지?")에 답합니다 |
| "버전 3", "버전 4" — 이름에 의미가 없어 목록을 봐도 모릅니다 | "카카오 · 프로덕트 디자이너 · 9/25" — 목록 자체가 정보입니다 |
| 언제 저장할지 사용자가 정해야 합니다 | 내보내기 버튼을 누르는 순간이 곧 저장 시점입니다. 따로 할 일이 없습니다 |

## 3. 흐름

```
편집기 → 내보내기 화면
          ├ [어디에 제출하나요?] 회사 ___  포지션 ___   (비우면 기록 안 함)
          └ PDF / HTML 내보내기  ─→  파일 + 제출 기록 1건
```

- 입력칸은 내보내기 버튼 **바로 위 한 줄**입니다. 모달로 막지 않습니다 —
  그냥 파일만 뽑고 싶은 사람도 있습니다. 비워 두면 기록하지 않습니다.
- 직무 전환으로 만든 포트폴리오면 공고의 회사·직무를 미리 채웁니다
  (`job_switch_runs` 에 공고가 있습니다).
- "파일 없이 기록만 남기기" 버튼도 둡니다 — 공개 링크(`/p/:id`)만 보낸 경우.

## 4. 무엇을 남기나

두 가지를 같이 남깁니다. 용도가 다릅니다.

| | 무엇 | 왜 |
|---|---|---|
| **결과물** | 내보낸 그 HTML (`TemplateFrame` 이 채워준 `filledHtml`) | "무엇을 냈는가"의 정답. 나중에 템플릿이 바뀌어도 그때 모습 그대로 |
| **데이터** | 포트폴리오 + 프로젝트 + 블록 JSON | "이 버전으로 새 포트폴리오 만들기"(복제)에 씀 |

**이미지는 결과물 HTML 안에 넣습니다(data URI).** URL로 두면 나중에 편집기에서
이미지를 지우는 순간 옛 제출본이 깨집니다(`deleteProjectImage` 가 파일까지
지움). 업로드 때 이미 축소돼 있어(`shrinkImage`, 긴 변 1600px) 장당 수백 KB
수준입니다. 한 건이 10MB를 넘으면 이미지를 빼고 경고합니다.

## 5. 데이터

```sql
portfolio_submissions (
  id uuid pk,
  user_id uuid references auth.users on delete cascade,
  -- 포트폴리오를 지워도 제출 기록은 남깁니다. 낸 사실은 사라지지 않습니다.
  portfolio_id uuid references portfolios on delete set null,
  portfolio_title text,          -- 지워진 뒤에도 목록에 보이도록
  company text,
  position text,
  jd_url text,
  job_switch_run_id uuid references job_switch_runs on delete set null,
  submitted_on date default current_date,
  note text,
  format text,                   -- 'pdf' | 'html' | 'link'
  lang text,                     -- 'ko' | 'en'
  html_path text,                -- Storage 'submissions' 버킷 경로
  snapshot jsonb,                -- { portfolio, projects, blocks }
  created_at timestamptz
)
```

- RLS: 본인 것만. **커뮤니티·공개 링크 어디에도 노출하지 않습니다** — 어느
  회사에 지원했는지는 재직 중 이직 준비에서 가장 민감한 정보입니다.
- Storage `submissions` 버킷은 **비공개**. 경로 `{userId}/{submissionId}.html`,
  정책은 다른 버킷과 같은 `(storage.foldername(name))[1] = auth.uid()`.
- 함께 고칠 곳: `delete-account` 가 이 버킷도 비우게(`purgeBucket`),
  `account.ts` 의 "내 데이터 내보내기" JSON에 제출 기록 포함.

## 6. 화면

- **포트폴리오별 제출 기록** — 지금의 `/library/portfolios/:id/versions`
  자리. 목록: 회사 · 포지션 · 날짜 · 형식. 누르면 그때 결과물을 읽기 전용
  iframe 으로 보여주고, [다시 받기] [이 버전으로 새 포트폴리오 만들기].
- **내 서재 카드**의 "버전 관리" → "제출 기록 N".
- **홈**의 가짜 "최근 AI 요청 상태" 자리를 **최근 제출 3건**으로 바꿉니다
  (CONTEXT.md 남은 할 일의 그 항목이 같이 해결됩니다).
- 줄글 안내 대신 회사명·날짜가 주인공인 목록입니다.

## 7. 만들지 않을 것 (1차)

- **지원 상태 관리**(서류 → 면접 → 결과), 마감 알림 — 채용 관리 도구가 됩니다.
  쓰임새를 보고 2차로 판단합니다.
- **두 제출본 비교(diff)** — 2차.
- **메일로 보내기** — 사용자의 메일에서 보내는 편이 낫습니다.

## 8. 비용

AI 호출이 없습니다. Storage 용량만 늘어납니다(한 건 수백 KB~수 MB).

## 9. 검증 방법

1. 제출 기록을 남긴 뒤 편집기에서 글과 이미지를 고치고 지워도, 기록의 결과물은
   그때 모습 그대로인가
2. 포트폴리오를 지워도 기록 목록에 남는가
3. 다른 계정에서 기록·파일 어느 것도 읽히지 않는가(RLS·Storage 정책)

## 11. 사용자 확인이 필요한 것

| 질문 | 기본값 |
|---|---|
| 지원 상태(서류/면접/결과)까지 1차에 넣을까 | 넣지 않음 |
